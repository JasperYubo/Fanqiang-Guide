  [STEP] 2 classify the sharing mechanism from current official client and platform evidence. Ordinary Android hotspot plus a VpnService icon is insufficient. On iOS, Personal Hotspot normally supplies cellular internet and is not a general WiFi-to-WiFi VPN router. Record the supported mechanism and exact version before enabling a shared route. If none is supported, leave sharing incomplete and offer a compatible downstream client or router workflow within the user's stated constraints.
  [STEP] 3 branch EXPLICIT_PROXY when the client documents a reachable local HTTP or SOCKS service and the downstream supports that setting. Keep the phone and target on a trusted reachable network; ordinary home WiFi can suffice without a new hotspot. Bind only to the intended local interface where supported, limit access to intended devices, use supported local authentication, and never expose an unauthenticated proxy through an internet-facing port or router forward. Enter any secret locally. Do not assume a 127.0.0.1 listener is reachable from another device.
  [STEP] 4 for EXPLICIT_PROXY, save the downstream's original proxy setting, enter the phone's observed reachable address, correct protocol and current port, then test an actual proxy-aware target app. HTTP CONNECT is a TCP proxy mechanism, not proof of UDP or all-app coverage. Determine whether the client sends the hostname or resolves it locally, and account for browser or app encrypted DNS.   [STEP] 5 branch DOCUMENTED_GATEWAY only when a current supported implementation explicitly handles downstream forwarding.   [STEP] 6 for an authorized documented gateway, verify the exact model, firmware, client release, permissions, selected upstream, downstream interface, supported IPv4/IPv6 and TCP/UDP behavior, and official start/stop cleanup. ::MODULE{VERIFY_SHARED|title:prove the requested downstream behavior without broad claims}
  [STEP] 1 establish that the test request originates on the intended downstream device and uses this shared path. Observe the selected WiFi or USB link and relevant route or proxy settings.   [STEP] 2 load the user's actual requested page content or app function on that device with certificate verification intact.   [STEP] 3 verify name resolution against the declared policy on the downstream: ordinary DNS, browser/app encrypted DNS, local versus proxy-side resolution, and the relevant address families. If the path cannot be observed, record that limitation and leave required DNS acceptance incomplete.
  [STEP] 4 separately test IPv4 and IPv6 when present, checking actual route and target success rather than assuming the phone's IPv4 result covers both. Never silently claim IPv6 blocked or tunneled from an IPv4-only test.
  [STEP] 5 test a user-required UDP function through this path, or a controlled UDP fixture when available. Record supported, failed or unverified separately from HTTPS/TCP.   [STEP] 6 safely stop and restart the host tunnel and sharing mechanism while observing the downstream.
